# Harfang 3D Architecture

> Harfang is a C++ engine that was designed to be driven from Python and Lua. That one decision shapes everything else: no base class to inherit, no callbacks to override, handles instead of pointers, free functions instead of methods, and a scene that is five flat arrays and a garbage collector.

All paths and line numbers refer to commit `abc8fc5de961` (v3.2.7+2, 2023-08-16) of `frameworks/harfang3d`, the checkout recorded in `notes/SUBMODULE-PINS.md`. Paths are relative to the `harfang/` source directory unless they start with `binding/`, `tools/` or `doc/`, or are the repository-root `CMakeLists.txt`.

## Key Insight

> **Harfang's core idea:** the public API is whatever a binding generator can express, so the engine is built from plain structs, 8-byte generational handles, and free functions that take a scene or a resource table as their first argument. The three bound languages, Python, Lua and Go, fall out of one 4,559-line description for free.

---

## The Problem: One Engine, Four Languages, No Framework Loop

Picture the brief. You are building a 3D engine for industrial visualization: simulators, embedded dashboards, VR training rigs. Your customers write Python, Lua or Go, not C++ (C++ plus those three are the four languages in the title; Lua also appears a second time, as the in-engine scripting VM for scene components), and they already have a main loop, a UI toolkit and a process model. They do not want your `App` class. They want a library they can call from inside their own loop, and they want the Python call to look like the C++ call so the documentation can be written once.

That brief kills the pattern every creative coding framework in this repository uses. openFrameworks and Cinder hand you `setup()`/`update()`/`draw()` and own the window, the clock and the event dispatch. Harfang cannot do that: a virtual method on a C++ base class does not survive a trip through a generated Python extension module, and a framework-owned loop fights the host application's loop. A grep for `class App` or `virtual void draw` across `harfang/` finds nothing.

The brief also kills the C++ idioms that make a scene graph pleasant to write by hand. Smart pointers, templates, inheritance hierarchies and iterators are all hard or impossible to bind. What binds well is small: integers, floats, strings, plain structs, opaque handles, and functions over them.

Harfang's answer is to accept those constraints as the design. The engine is three static libraries plus a binding description, and the binding description is the contract that the C++ code is written to satisfy.

## The Mental Model: Three Libraries and a Skin

Think of Harfang as a stack of three static libraries with a generated skin on top.

```
┌─────────────────────────────────────────────────────────────┐
│  hg_python / hg_lua / hg_go      generated by FABGen from   │
│                                  binding/bind_harfang.py    │
├─────────────────────────────────────────────────────────────┤
│  engine      scene, render pipeline, assets, audio,         │
│              physics (Bullet), navigation (Recast),         │
│              VR (OpenVR/OpenXR), ImGui, scene Lua VM        │
│              links: bgfx, imgui, json, meshoptimizer, ...   │
├──────────────────────────┬──────────────────────────────────┤
│  platform                │  script                          │
│  window + input          │  Lua 5.4 VM wrapper              │
│  glfw/sdl/win32/osx/...  │  (LuaObject, watchdog)           │
├──────────────────────────┴──────────────────────────────────┤
│  foundation  math, color, containers, I/O interfaces,       │
│              profiler, log, time, rand, easing              │
│              links: nothing engine-related                  │
└─────────────────────────────────────────────────────────────┘
```

The CMake files make the layering explicit. `foundation` links only system libraries (`foundation/CMakeLists.txt:162-172`). `platform` links `foundation` and the windowing backend: GLFW on desktop, the NDK glue on Android, plain GL on Emscripten (`platform/CMakeLists.txt:85-103`). `script` links `foundation` and Lua (`script/CMakeLists.txt:7-8`). `engine` links all three plus bgfx, Dear ImGui, nlohmann json, meshoptimizer and, tellingly, the generated Lua binding `bind_hg_lua`, all publicly (`engine/CMakeLists.txt:121`). OpenAL is private and skipped on web builds (`:123-125`); Bullet, Recast, OpenVR and OpenXR are private and sit behind `HG_ENABLE_*` options (`:129-147`). Nothing below `engine` knows that a GPU exists.

| Layer | Directory | Owns | Does not know about |
|-------|-----------|------|---------------------|
| foundation | `foundation/` | `Vec3`, `Mat4`, `Color`, `gen_ref`, `vector_list`, `Reader`/`Writer`, `Signal`, profiler, log | windows, GPU, scenes |
| platform | `platform/` | `Window*`, monitors, mouse/keyboard/gamepad/VR controller readers | bgfx, scenes |
| script | `script/` | `lua_State` lifetime, `LuaObject`, execution watchdog | scenes, rendering |
| engine | `engine/` | `Scene`, `PipelineResources`, forward pipeline, assets, audio, physics, scripting glue | the host application's loop |

Two things are worth noticing about this picture before going deeper. First, there is no "application" layer. The host writes the loop. Second, the skin on top is not hand-written. It is generated from a single Python file, and that file's limitations are the reason the layers below look the way they do.

## Why Everything Comes in Pairs: The Reader Abstraction

Open any engine header and you will see the same function three times: `LoadModelFromFile`, `LoadModelFromAssets`, and a `LoadModel` that takes a `Reader` and a `ReadProvider` (`engine/render_pipeline.h:431-433`). The same triple appears for textures, materials, pipeline programs, scenes, scripts and AAA configurations. It looks like boilerplate. It is actually the engine's only I/O abstraction, and it is worth understanding because it explains the asset system.

`Reader` and `ReadProvider` are structs of plain function pointers, not virtual interfaces:

**File:** `foundation/rw_interface.h:25-32`, `:102-106`

```cpp
struct Reader {
	size_t (*read)(Handle h, void *data, size_t size);
	size_t (*size)(Handle h);
	bool (*seek)(Handle h, ptrdiff_t offset, SeekMode mode);
	size_t (*tell)(Handle h);
	bool (*is_valid)(Handle h);
	bool (*is_eof)(Handle h);
};

struct ReadProvider {
	Handle (*open)(const char *path, bool silent);
	void (*close)(Handle hnd);
	bool (*is_file)(const char *path);
};
```

A `Handle` is 16 opaque bytes in release builds (`rw_interface.h:18-23`; debug builds add a flag). Two global pairs exist: `g_file_reader`/`g_file_read_provider` for the local filesystem and `g_assets_reader`/`g_assets_read_provider` for the asset system (`engine/assets_rw_interface.h:9-10`). Every `*FromFile` and `*FromAssets` function is a one-line forwarder that picks a pair (`engine/render_pipeline.cpp:659-667`). The reason for function pointers rather than an abstract class is the same reason as everywhere else: a struct of function pointers is C-compatible and binds, a virtual interface does not.

The asset side is small. `AddAssetsFolder` pushes a directory onto the front of a deque (`engine/assets.cpp:36-43`), and `FindAssetPath` walks that deque front to back (`:136-145`). The consequence is easy to miss: the folder you add last wins a name collision, the reverse of most mount lists. `AddAssetsPackage` opens a zip archive through miniz (`:62-73`). One detail matters for memory: opening an asset from a package extracts the whole entry to the heap (`mz_zip_reader_extract_to_heap`, `:165`) and then serves reads from that buffer (`:113-131`). Packages are convenient, not streamed.

## The Scene: Five Arrays, a Generation Counter and a Garbage Collector

Here is where the binding constraint pays off most visibly. A conventional C++ scene graph is a tree of heap-allocated node objects linked by pointers. Harfang's `Scene` is a handful of flat arrays indexed by small integers.

### The handle

Everything the user holds is a `gen_ref`, eight bytes:

**File:** `foundation/generational_vector_list.h:10-12`

```cpp
struct gen_ref {
	uint32_t idx{0xffffffff}, gen{0xffffffff};
};
```

Think of a coat check that reuses hooks but never reuses ticket numbers: a ticket for a coat that was already collected still names a hook, but the number printed on it no longer matches the number on the hook. The container behind the handle, `generational_vector_list<T>`, is a `vector_list<T>` (a slot array with a free list and index recycling, described in the comment at `foundation/vector_list.h:12-27`, class at `:28`) plus a parallel `std::vector<uint32_t> generations`. Adding an element returns `{idx, generations[idx]}` (`generational_vector_list.h:23-28`). Removing it increments `generations[idx]` before freeing the slot (`:37-42`). A handle is valid only if its generation still matches (`:59`). So a slot can be reused for a new element and every stale handle to the old one keeps failing `is_valid`. That is the whole trick, and it is the same trick rend3's handle types and Filament's `Entity` use. Harfang's class is about 50 lines (`generational_vector_list.h:21-68`) with no dependencies beyond `vector_list`.

### The storage

`Scene` keeps one `generational_vector_list` per component kind, plus one for nodes:

**File:** `engine/scene.h:698-704`, `:787-791`

```cpp
struct Node_ { // 52B
	std::string name; // 8B
	ComponentRef components[NCI_Count]; // 40B
	uint32_t flags; // 4B
};
generational_vector_list<Node_> nodes;
// ...
generational_vector_list<Transform_> transforms;
generational_vector_list<Camera_> cameras;
generational_vector_list<Object_> objects;
generational_vector_list<Light_> lights;
generational_vector_list<RigidBody_> rigid_bodies;
```

A node is a name, five component slots and some flags. `NCI_Count` is five (`scene.h:163`): Transform, Camera, Object, Light, RigidBody. Those are the "one per node" components, and they live inline in the node. Collisions and scripts, which a node can have several of, live in their own lists and attach through side maps from `NodeRef` to a vector of refs (`scene.h:801-802`, `:810-813`). Instances are one per node but also kept out of the inline slots, in a `NodeRef` to `ComponentRef` map (`:823-826`). It is an honest split: the five hot components get the fast path, the rest get a `std::map`.

### What the user actually holds

The `Node`, `Transform`, `Camera` and friends in `engine/node.h` are not the data. Each is a scene reference plus a `gen_ref`:

**File:** `engine/node.h:282-290`, `:388-389`

```cpp
struct Node { // 16B on 64 bit
	bool IsValid() const;
	// ... getters and setters that forward to the Scene ...
	intrusive_shared_ptr_st<SceneRef> scene_ref;
	NodeRef ref;
};
```

`SceneRef` is a tiny refcounted box holding a `Scene *` (`scene.h:908-911`). The scene constructor allocates it (`scene.cpp:25`) and the destructor nulls the pointer (`:27-30`), so a `Node` outliving its scene reports invalid instead of dereferencing freed memory (`node.cpp:12`). This is the pattern a Python object needs: a `hg.Node` can sit in a list after the scene is gone, and asking it anything is safe.

Every method on `Node` or `Transform` is a forwarder into `Scene`. `Transform::SetPos` becomes `Scene::SetTransformPos(ComponentRef, Vec3)` (`scene.h:246`). That is why `Scene` has roughly 300 public methods: the whole component API is spelled twice, once as a value-type convenience and once as the real entry point that takes a handle.

### Creating, destroying, collecting

Let's trace the lifecycle, because the one surprising step is at the end.

1. `scene.CreateNode("lamp")` does nothing but `nodes.add_ref({name})` (`scene.cpp:468`). The node has five invalid component refs.
2. `scene.CreateTransform()` adds a `Transform_` to `transforms` and returns a handle. `node.SetTransform(t)` writes that handle into slot `NCI_Transform` of the node (`scene.h:720-723`).
3. `scene.DestroyNode(node)` is `nodes.remove_ref(ref)` (`scene.cpp:469`). The node is gone. **The transform is not.** Nothing walked the node's slots.
4. `scene.GarbageCollect()` runs a mark-and-sweep: for each component list, mark every slot some live node points to, then destroy the unmarked ones (`scene.cpp:92-116`, the `GC_Components` macro). The side-mapped collisions and instances get the same treatment with their maps (`:118-152`).

The unit test at `tests/engine/scene.cpp:27-33` is the clearest statement of the contract: create a transform with no node, call `GarbageCollect`, expect one removal and an invalid handle. Component destruction is deferred and explicit. The documentation comment on `GarbageCollect` says why: batch your node removals and collect once (`scene.h:181-187`).

### World matrices: a memoized recursion over a flat array

Transforms store local TRS plus a parent `NodeRef` (`scene.h:734-737`). World matrices are not stored in the component. They live in `std::vector<Mat4> transform_worlds`, sized to the transform list's capacity and indexed by transform slot (`scene.h:869`, `scene.cpp:280-284`). `ComputeWorldMatrices` iterates every live transform (`:286-289`) and calls a memoized recursion:

**File:** `engine/scene.cpp:263-277`

```cpp
void Scene::ComputeTransformWorldMatrix(uint32_t idx) {
	if (!transform_worlds_updated[idx]) {
		const auto &trs = transforms[idx];
		auto world = TransformationMat4(trs.TRS.pos, trs.TRS.rot, trs.TRS.scl);

		const auto parent_ref = GetNodeComponentRef_<NCI_Transform>(trs.parent);
		if (transforms.is_valid(parent_ref)) {
			ComputeTransformWorldMatrix(parent_ref.idx);
			world = transform_worlds[parent_ref.idx] * world;
		}

		transform_worlds_updated[idx] = true;
		transform_worlds[idx] = world;
	}
}
```

No tree traversal, no sorted order: each transform recurses to its parent on demand and the `updated` bitmap stops double work. The renderer later indexes `transform_worlds` directly with the transform slot index it stored in each display list (`scene.cpp:361-363`), so the "scene graph" and the "render list" share one array of matrices with no copying.

`Scene::Update` is five lines (`scene.cpp:307-315`): swap current and previous matrices, clear the `updated` flags, advance animations, compute, fix up. The previous-frame matrices feed the AAA pipeline's velocity buffer.

One reading of the code, not confirmed by running it: `FixupPreviousWorldMatrices` is meant to copy a current matrix into the previous slot when the previous one was never computed, but the line that should assign uses `==` (`scene.cpp:303`). The function compares and discards. If that reading is right, a transform created this frame has whatever stale value the swapped vector held at that index as its "previous" matrix, which would feed the velocity buffer for one frame. **This is untested.**

## Systems Are Guests, Not Members

`Scene` contains no Lua state and no physics world. Those live in separate objects, `SceneLuaVM` (`engine/scene_lua_vm.h:22`) and `SceneBullet3Physics` (`engine/scene_bullet3_physics.h:29`), and a set of free functions in `engine/scene_systems.h` keep them in step with the scene. The update order is fixed in one place:

**File:** `engine/scene_systems.cpp:152-179`

| Step | Call | What it does |
|------|------|--------------|
| 1 | `scene.StorePreviousWorldMatrices()`, `ReadyWorldMatrices()` | Swap matrix vectors, clear flags |
| 2 | `scene.UpdatePlayingAnims(dt)` | Write animated TRS values into components |
| 3 | `physics->SyncTransformsFromScene`, `StepSimulation`, `SyncTransformsToScene` | Only if a physics system was passed: push kinematic bodies in, step Bullet, pull dynamic bodies out |
| 4 | `CollectCollisionEvents`, `SceneScriptsOnCollisionCall` | Only if a contacts list was also passed: deliver contacts, and with a VM, call Lua `OnCollision` (`:165-170`) |
| 5 | `SceneScriptsOnUpdateCall(*vm, scene, dt)` | Only with a VM: call Lua `OnUpdate` on every script component |
| 6 | `scene.ComputeWorldMatrices()`, `FixupPreviousWorldMatrices()` | Resolve the hierarchy once, after everything has written to it |

The pointer parameters are optional, and the public `SceneUpdateSystems` overloads (`:181-204`) just fill in `nullptr` for the systems you did not create. Garbage collection cascades the same way: collect the scene, then let physics drop bodies whose nodes are gone, then let the VM call `OnDestroy` on orphaned scripts (`:208-224`).

Think of it as a scene that publishes its state and systems that subscribe by polling. There is no observer list. Each system scans the scene for what it cares about during its sync call. That costs a pass per system per frame, and buys a scene type with zero dependencies on Bullet or Lua, which is what lets `HG_ENABLE_BULLET3_SCENE_PHYSICS` be a CMake switch rather than a refactor.

The Lua side deserves one note. Scripts are scene components holding a path and parameters (`scene.h:805-808`); the VM compiles them into per-script environment tables (`scene_lua_vm.h:28`, `:60`). `script/lua_vm.h:83-86` installs an execution watchdog with a timeout, so a script stuck in a loop cannot hang the host. For an engine meant to be embedded in someone else's process, that is a deliberate safety rail.

## PipelineResources: One Table for Everything the GPU Owns

GPU-side resources never appear as pointers in the API either. `PipelineResources` holds four `ResourceCache` tables:

**File:** `engine/render_pipeline.h:454-470`

```cpp
struct PipelineResources {
	ResourceCache<PipelineProgram, PipelineProgramRef> programs;
	ResourceCache<Texture, TextureRef> textures;
	ResourceCache<Material, MaterialRef> materials;
	ResourceCache<Model, ModelRef> models;

	std::deque<TextureLoad> texture_loads;
	std::map<gen_ref, bgfx::TextureInfo> texture_infos;
	std::deque<ModelLoad> model_loads;
	std::map<gen_ref, ModelInfo> model_infos;
	// ...
};
```

`ResourceCache` is the same `generational_vector_list` wrapped with a name-to-handle map (`engine/resource_cache.h:18-141`). `Add(name, res)` returns the existing handle if the name is already present (`:28-36`), so loading the same model twice yields the same `ModelRef` and one GPU buffer. A `TextureRef` is just a `gen_ref` in a type-tagged wrapper (`:12-16`).

The load queues turn blocking loads into budgeted ones. `QueueLoadModel` registers the name and returns a handle immediately (`render_pipeline.cpp:1653-1661`; the `FromAssets` wrapper is `:1665-1667`); the model is empty until `ProcessLoadQueues` runs (`:2338-2344`). That drains the model queue and then the texture queue, each against its own time budget of 4 ms by default (`render_pipeline.h:543`; the model loop at `.cpp:1619-1651`). The budget is checked after each entry, so one large model can overshoot it, and a frame that drains both queues can spend about 8 ms. Scene loading can either queue or load inline through the `queue_model_loads` and `queue_texture_loads` flags that thread through every loader (`scene.h:831-832`). This is Harfang's whole answer to asynchronous asset loading: no threads, a queue drained on the main thread between frames.

There is one lifetime hazard worth knowing. A `ModelDisplayList` carries a raw `const Material *` into an object's material vector (`render_pipeline.h:577-582`, filled at `scene.cpp:353-363`). It is valid only until the scene's object storage reallocates. The renderer rebuilds display lists every frame, so in practice the pointer never ages, but you cannot keep one.

## The Binding Description Is the API Contract

Everything above was shaped by `binding/bind_harfang.py`. It helps to see what that file actually does.

The file is a sequence of `bind_*` functions, one per subsystem, called in order from the entry point (`bind_harfang.py:4513-4557`): log, time, file, assets, math, window system, color, picture, render, forward pipeline, scene, physics, Lua VM, scene systems, input, ImGui, audio, VR, geometry builders, navigation. Each one declares classes, members, free functions and enums to FABGen with calls such as:

**File:** `binding/bind_harfang.py:924-928`, `:950`

```python
scene = gen.begin_class('hg::Scene', noncopyable=True)
scene_view = gen.begin_class('hg::SceneView')

node = gen.begin_class('hg::Node')
node._inline = True
# ...
gen.bind_method(transform, 'GetPosRot', 'void', ['hg::Vec3 &pos', 'hg::Vec3 &rot'], {'arg_out': ['pos', 'rot']})
```

Three features of that vocabulary explain three features of the C++:

- **`_inline = True`** marks `Node` as a value type the generated code copies rather than wraps. That is only possible because `Node` is 16 bytes of handle (`node.h:282`). Make `Node` a heap object with virtual methods and this line stops working.
- **`arg_out` and `arg_in_out`** turn C++ reference parameters into extra Python return values. `GetWindowClientSize(win, int &w, int &h)` becomes `w, h = hg.GetWindowClientSize(win)` (`bind_harfang.py:797`). The render pipeline's `bgfx::ViewId &view_id` parameter, which every submit function increments, is declared `arg_in_out` (`:1570`), so the Python caller writes `view_id, views = hg.SubmitSceneToPipeline(view_id, ...)`. The C++ convention of threading a counter by reference is a direct consequence of needing a binding-friendly way to say "this pass consumed some view ids".
- **`gen.typedef('bgfx::ViewId', 'uint16_t')`** (`:4496`) and **`gen.bind_function('bgfx::frame', 'uint32_t', [], bound_name='Frame')`** (`:2150`) expose two bgfx symbols directly. Python's `hg.Frame()` is `bgfx::frame()`. Harfang does not wrap the frame boundary; it hands the host the real one.

The dependency runs in the other direction too. `engine/scene_forward_pipeline.cpp:12` includes `fabgen.h`, and `binding/fabgen.h:5` defines the `OwnershipPolicy` enum the generator uses. The engine knows the binding generator's vocabulary. That is unusual, and it is the clearest evidence that the binding was not added after the fact.

The documentation follows the same path. `doc/CMakeLists.txt:3-13` runs FABGen's `bind.py --xml` over the same description to produce `api.xml`, which the documentation build combines with the 951 one-paragraph pages under `doc/doc/` (for example `doc/doc/Scene.md` is a single sentence pointing at a manual page). The signature in the docs cannot drift from the signature in Python because both come from one file.

## Platform and Input: Opaque Pointers and Named Readers

The platform layer follows the same rules with an older flavor. `Window` is declared and never defined for the user; the public API is free functions over `Window *` (`platform/window_system.h:61-119`). The GLFW backend does not even wrap anything: it defines `Window` as a one-field dummy struct and casts `GLFWwindow *` to and from it (`platform/glfw/window_system.cpp:154-156`, `:168-191`). `GetWindowHandle` hands the native handle to bgfx (`:189` on the non-Wayland branch, consumed at `engine/render_pipeline.cpp:2652`).

Input is a registry of named readers. `ReadMouse("default")` and `ReadKeyboard("default")` return snapshot structs (`platform/input_system.h:20-31`, `:187-197`). A backend registers readers under names at startup; GLFW registers `"default"` everywhere and adds `"raw"` mouse and keyboard readers on Windows only (`platform/glfw/input_system_glfw.cpp:576-585`). Polling a snapshot struct rather than subscribing to events is, again, the shape that binds cleanly and that a host loop can call whenever it likes.

## Gotchas and Sharp Edges

- **Garbage collection is manual.** Destroying a node orphans its components until `GarbageCollect` (or `SceneGarbageCollectSystems`) runs. Forgetting it leaks components. The renderer will not draw them, because `GetModelDisplayLists` iterates nodes (`scene.cpp:330-340`), but their GPU resources stay alive.
- **`FixupPreviousWorldMatrices` appears to be a no-op**; see the world-matrix section above.
- **`UniformSetValue` copies create GPU uniforms.** The copy constructor destroys and recreates a `bgfx::UniformHandle` (`render_pipeline.cpp:100-110`). The source comment says "burn it with fire" (`render_pipeline.h:270`). Pass these by reference.
- **Display lists hold raw material pointers** (`render_pipeline.h:578`). Rebuild them every frame; never cache them across scene edits.
- **Asset packages are decompressed whole on open** (`assets.cpp:165`). A 200 MB mesh in a zip costs 200 MB of heap while it is open.
- **Folder precedence is "last added wins"** (`assets.cpp:39`, `:139-143`), the opposite of what a mount list usually does.
- **`HG_EMBEDDED` has no consumer.** CMake forces it on for ARM and adds the define (`CMakeLists.txt:79`, `:173-174`), but a search of `harfang/`, `binding/` and `languages/` finds no code reading it. Treat it as a hook rather than a feature.

## What Flux Should Take From This

| Pattern | Verdict | Why |
|---------|---------|-----|
| Generational handles with a parallel generation vector | Adopt | 70 lines, no dependencies, same guarantee as rend3's handles. Flux's operator graph needs stale-handle safety and this is the minimum that gives it |
| Public types as (owner ref, handle) pairs that forward to the owner | Adopt for the scripting surface | It is what lets a scripted object outlive its owner safely. Rust would use a `Weak` or an arena id rather than an intrusive refcount, but the shape is right |
| Binding description as the API contract, with docs generated from it | Adopt the principle | Flux has not picked a scripting layer, but if it does, deciding the API from the binding side first is what kept Harfang's three languages identical |
| Systems as external objects synced by free functions | Modify | Harfang's polling sync costs a scan per system per frame. Keep the zero-dependency scene, but let systems register for the component kinds they want instead of scanning |
| Deferred, explicit garbage collection | Avoid as a user-facing requirement | Correct and simple, but every tutorial has to remember to call it. Flux should collect at a well-defined point in its own frame |
| Function-pointer `Reader`/`ReadProvider` | Modify | The idea (one I/O interface, files and packages behind it) is right; a Rust trait object does it without the `*FromFile`/`*FromAssets` duplication |
| Budgeted main-thread load queues | Adopt as the fallback path | Flux will want real async loading, but a time-budgeted queue is the simplest thing that keeps a web build responsive without threads |
