## Why Study This

Harfang is not a creative coding framework. It is an industrial visualization engine aimed at embedded systems, simulators and VR, and that is what makes it a useful contrast. Where openFrameworks and Cinder hand the user a `setup()`/`draw()` skeleton and an immediate-mode drawing API, Harfang hands the user a retained scene, a handful of pipeline functions and nothing else: the application owns its own loop and calls `SubmitSceneToPipeline` each frame. The result is a small, flat C API surface that can be bound to several scripting languages without loss.

Three parts of the design speak directly to Flux.

**One core, many languages.** The Python, Lua and Go modules are not hand-written. A single 4,559-line FABGen description (`binding/bind_harfang.py`) declares every bound type and function, and the generator emits the extension module for each language. The same description feeds the API documentation: `doc/CMakeLists.txt:3-13` runs FABGen's `bind.py --xml` over it to produce `api.xml`, which the documentation build merges with the hand-written pages under `doc/doc/`. For a Rust framework that wants a scripting layer, Harfang is the most complete open example of a binding-first API: every function has to be expressible as plain values, handles and structs, which forces the kind of API discipline Flux has been circling in `insights/api-recommendations.md`.

**A data-oriented scene without an ECS framework.** `Scene` (`harfang/engine/scene.h:173`) stores each component kind in its own `generational_vector_list` (`scene.h:704-823`: nodes, transforms, cameras, objects, lights, rigid bodies, collisions, scripts, instances). Handles are `gen_ref` index-plus-generation pairs (`harfang/foundation/generational_vector_list.h:10`), and the public `Node`, `Transform`, `Camera`, `Object`, `Light` and `RigidBody` types in `node.h` are handle wrappers holding a scene reference and a `gen_ref` (16 bytes on 64-bit, per the comments in `node.h`), not the data itself. This is the pattern rend3 and Filament reach for in different ways; here `scene.h` is about a thousand lines and depends on nothing outside `foundation/`.

**Two renderers over one scene.** The forward pipeline ships in a low-spec PBR form and an "AAA" form (`ForwardPipelineAAA`, `scene_forward_pipeline.h:61`) that adds screen-space GI and reflections, temporal accumulation, TAA, motion blur, bloom and depth of field, each in its own small file (`ssgi.cpp`, `ssr.cpp`, `taa.cpp`, `motion_blur.cpp`, `bloom.cpp`, `dof.cpp`, `hiz.cpp`). A SAO module exists (`sao.cpp`) but its hook in the AAA chain is compiled out (`scene_forward_pipeline.cpp:729-737`). The two share `PipelineResources`, `Material` and `Model` (`render_pipeline.h`), and bgfx's explicit view ids are threaded through every submit call as `bgfx::ViewId &view_id`. It is a compact case study in how a pipeline can grow in quality tiers without the scene representation knowing.

Two more reasons are practical. Harfang sits on bgfx, which the fr_public notes name as the runtime-switchable alternative to Altona's compile-time backend selection, so it gives this repository its first bgfx-based engine to read against Filament's command stream and wgpu. And its asset compiler (`tools/assetc/`) drives shaderc, texturec, luac, cmft, recastc and bulletc (`assetc.cpp:118`) to precompile everything per backend, which is the ahead-of-time stance Filament takes with matc, applied to a whole project rather than to materials alone.

## What Is Not in the Repository

- **Shader sources.** The engine loads compiled bgfx programs from the asset tree at runtime (`LoadProgramFromAssets`, `render_pipeline.h:104-106`); no `.sc` shader source is in the repository (`find . -name '*.sc'` outside `extern/` returns nothing). Pipeline notes will have to read the C++ side and the bgfx shader conventions, or fetch Harfang's shader package into `references/harfang3d/`.
- **FABGen itself.** The generator is a separate repository (`ejulien/FABGen`) that the build expects at `HG_FABGEN_PATH` (`CMakeLists.txt:60`). The binding description is here; the code generator is not.
- **Nested submodules.** Eleven are declared in `.gitmodules` (bgfx, bx, bimg, glfw, OpenAL Soft, OpenVR, OpenXR, cmft, Recast, meshoptimizer, assimp). A plain `--init` of this repository leaves all of them empty. The bgfx trio was initialized for the rendering-pipeline note, which cites `bgfx.h`, `bgfx_p.h` and `bgfx_shader.sh` at the pinned commit; the command is below the pin table.
- **Harfang Studio.** The editor is a commercial product and is not in the repository.

## Key Areas to Study

| Area | Where | Relevance to Flux |
|------|-------|-------------------|
| Binding-first API | `binding/bind_harfang.py`, `languages/hg_python`, `languages/hg_lua`, `languages/hg_go` | What an API must look like to be generated into three languages; how documentation is attached |
| Handle-based scene | `harfang/engine/scene.h`, `node.h`, `foundation/generational_vector_list.h` | Generational handles and per-component lists without an ECS crate |
| Pipeline resources | `harfang/engine/render_pipeline.h` | `PipelineResources` as the single owner of programs, materials, textures and models; 4-byte display lists |
| Forward pipeline tiers | `forward_pipeline.h`, `scene_forward_pipeline.h`, the post-process files | Low-spec and AAA tiers over the same scene; how bgfx view ids are allocated per pass |
| bgfx as backend | `extern/bgfx/` (submodule), `render_pipeline.cpp` | Runtime backend selection with sorted draw submission; compare with Filament's command stream and wgpu |
| Asset compiler | `tools/assetc/assetc.cpp`, `harfang/engine/assets.h` | Per-backend precompilation of shaders and textures; asset folders vs packages |
| Scene serialization | `scene_load_json.cpp`, `scene_load_binary.cpp`, `tools/gltf_converter/` | Dual JSON and binary scene formats; glTF import and export (relevant to `research/open-formats/`) |
| Embedded Lua | `harfang/script/lua_vm.h`, `engine/scene_lua_vm.h` | Scripts as scene components, an execution watchdog (`lua_vm.h:83`) |
| Foundation | `harfang/foundation/` | Math, color, easing, `rect_packer.h`, `signal.h`, `profiler.h`: a self-contained base layer with no external dependencies |

## Repository Structure

```
harfang3d/
├── harfang/
│   ├── foundation/      # Math, color, I/O interfaces, containers, profiler (no engine dependencies)
│   ├── platform/        # Window and input systems: glfw, sdl, win32, osx, posix, android
│   ├── engine/          # Scene, render pipeline, forward pipeline and post-processes,
│   │                    # assets, audio, physics (Bullet), navigation (Recast), VR (OpenVR/OpenXR),
│   │                    # Dear ImGui integration, scene Lua VM, loaders
│   ├── script/          # Lua VM wrapper
│   ├── tests/           # Unit tests (acutest)
│   └── version.txt      # 3.2.7
├── binding/
│   └── bind_harfang.py  # FABGen description of the whole public API
├── languages/           # Python wheel, Lua module and Go module build rules
├── tools/
│   ├── assetc/          # Asset compiler driving shaderc, texturec, luac, cmft, recastc, bulletc
│   ├── gltf_converter/  # glTF importer and exporter
│   ├── assimp_converter/
│   └── fbx_converter/   # Requires the proprietary Autodesk FBX SDK
├── doc/doc/             # 953 markdown pages, one per bound function or type
├── extern/              # Vendored and submoduled dependencies; extern/versions.txt lists them
└── CMakeLists.txt       # HG_* options: bindings, tools, physics, VR, Emscripten
```
