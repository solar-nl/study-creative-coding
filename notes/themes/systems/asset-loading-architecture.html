1The design problem

Today, file loading in Flux is ad-hoc: an operator calls std::fs::read with a raw path and decodes the bytes inline. Before that pattern spreads across LoadTexture, LoadMesh, LoadShader and the audio/CSV/JSON loaders still to come, we want a shared substrate. The working hypothesis splits file loading into two layers:

Resolution logical asset path → raw bytes. Format-neutral. Backend swaps: filesystem in the editor, bundle in the packed runtime.
→
Decode raw bytes → typed asset. Inherently per-type. Lives with each asset's domain (texture / mesh / shader).
→
Typed asset consumed by the operator graph as an output value or a cache handle.

The question this study answers: does that split hold up against how established frameworks actually solve the problem? Each framework is examined along nine dimensions — path & resolution model, resolution/decode separation, where the abstraction lives, handles & lifetime, hot-reload, caching & dedup, sync vs async, bundling, and error handling — with particular attention to three Flux constraints that frameworks routinely violate: Rust ownership, a synchronous graph evaluator with no async runtime in the hot path, and the editor + bundle duality.

Bottom line, stated up front

The split holds. It recurs — independently — in every framework that solves asset loading well, and its absence is the single best predictor of the designs that aged badly. But the split is not perfectly clean: decode is not a pure bytes → asset function — formats like glTF, OBJ and HLSL reference sibling files, so the decode layer needs a controlled capability to re-enter resolution. The detail that matters most for Flux is not whether to split, but how the synchronous evaluator obtains an asset — and there the closest architectural analogue (tixl) diverges sharply from the closest language analogue (Bevy).

4Deep dives — what is genuinely novel

Bevy — the AssetReader / AssetLoader split closest language match

Bevy draws exactly the line Flux proposes, and a mature Rust engine converging on the same boundary is the strongest available evidence that the hypothesis is sound. AssetReader is a trait whose only job is "translate a logical path into a byte stream" — it is format-neutral and has implementations for the native filesystem, the web, binary-baked bytes (EmbeddedAssetReader) and Android's asset manager. AssetLoader is the other trait — load(reader, settings, ctx) → Result<Asset, Error> — and it is per-type. They meet only at the top, inside AssetServer::load(): pick a source, get its reader, read bytes, pick a loader by extension, decode. GK

The boundary leaks — and the leak is the lesson

Bevy's split is not a pure bytes → asset function. A glTF file references external .bin buffers and texture images, so AssetLoader::load receives a LoadContext through which the loader can call read_asset_bytes(path) — re-entering the resolution layer — or load::<T>(path), which recursively kicks off another full resolve+decode and registers a dependency. Decode is therefore bytes + a capability to resolve more paths → asset. Flux must decide consciously where that capability lives.

The editor-vs-shipped split is expressed as unprocessed vs processed readers on each AssetSource, not as a separate code path. The background AssetProcessor reads a source asset, consults a .meta sidecar (loader settings + chosen processor), runs a transform, and writes an optimised artifact into imported_assets/. The shipped game reads the processed reader. What Flux should not copy is the consequence of Bevy's async-first design: load() returns a Handle<T> instantly while the data arrives "some frame later" — a model that only works because an ECS world ticks every frame and consumers re-query via AssetEvent. A Flux LoadTexture operator must produce a real output during evaluate(). The "handle is a promise" pattern leaks async into every downstream operator.

tixl — resolution as packages, hot-reload through the graph closest analogue

tixl is the single most load-bearing reference in this study because it shares all three Flux constraints: it is a node graph, it has the editor↔export duality, and its evaluation is synchronous. Its ResourceManager is not a registry of loaded assets — it is a path-resolution engine plus factory methods. TryResolvePath walks a priority-ordered list of IResourcePackage roots; TryGenerate<T> is the per-type decode delegate. That is Flux's split, in a shipping node-graph tool. visual-programming/tixl/Core/Resource/ResourceManager.cs:25

The editor↔export split is purely additive

tixl does not have a separate "bundle" code path. Both the editor and the exported Player call the identical TryResolvePath algorithm. What differs is only which IResourcePackage instances are registered: the editor registers live filesystem packages each carrying a ResourceFileWatcher; the Player registers read-only packages with FileWatcher = null. The export step walks the graph for file-path inputs, resolves each, and copies the file into Operators/<namespace>/Resources/<relative> — so the same relative path resolves identically in both worlds. This is the cleanest answer in the entire study to Flux's editor + bundle duality.

tixl is also the only framework here that propagates a file change correctly through a node graph. The chain: an OS FileSystemWatcher fires on a background thread → ResourceFileWatcher queues the event → every frame the editor drains the queue on the main thread after a 394 ms debounce → FileResource.FileChanged fires → Resource<T>.MarkFileAsChanged() resets the Lazy<T?> and calls DirtyFlag.ForceInvalidate() on every registered dependent slot → downstream operators re-evaluate next frame. The async part is confined to the OS watch thread; the propagation is synchronous and frame-aligned. Operators explicitly declare their dependent slots (_textureResource.AddDependentSlots(Texture)). For a synchronous graph evaluator, this is a near drop-in template.

three.js — the loader triad and the setURLModifier hook

three.js implements Flux's hypothesis as three tiers with almost no overlap. FileLoader is the only class that touches the network — given a resolved URL it returns bytes; it does no type-specific logic because it cannot know the type. Typed loaders (TextureLoader, GLTFLoader, FontLoader…) each instantiate a FileLoader, then call their own parse(buffer) — the decode step. LoadingManager sits above both and knows nothing about formats: it tracks progress and rewrites URLs. libraries/web/threejs/src/loaders/

setURLModifier is a pluggable resolution layer in miniature

LoadingManager.setURLModifier(fn) installs a single (url) → url function called before every fetch. three.js's own documentation shows using it to map logical filenames to in-memory blobs via URL.createObjectURL — i.e. the loaders above supply logical names, the modifier rewrites them to physical sources, and the typed decoders below never know the difference. That is exactly Flux's resolution layer. Its weakness is instructive too: there is only one modifier (last-writer-wins), so it cannot express "editor backend" and "bundle backend" simultaneously. Flux needs a trait object selected at startup, not a single mutable function.

Processing & p5.js — making async loading look synchronous

Both confront the same tension Flux faces — users want let img = load("x.png") without callbacks — and solve it two different ways. Processing's createInputRaw() is a fixed-priority waterfall (data/ folder → sketch root → JAR ClassLoader resource → URL). The fourth step is the key trick: when a file is not on disk, it falls through to getResourceAsStream("data/"+name), so the exact same filename string resolves to a filesystem file in development and a JAR resource in an exported app — the editor-vs-shipped split is invisible to caller code. notes/per-framework/processing/, frameworks/processing/core

p5.js's preload() barrier — a load phase, not an async API

p5.js converts inherently-async web loading into a synchronous-feeling API with a counter-based global barrier. A registry (_preloadMethods) lists every load* function; before preload() runs, each is wrapped to increment _preloadCount; each completion decrements it; setup() cannot run until the count hits zero. The load functions return empty objects immediately and are populated in place before the barrier lifts. The mechanism does not port to Rust — but the concept does: a "preload phase" where all loads are initiated, followed by a "run phase" where assets are guaranteed ready, is a viable model for Flux's synchronous evaluator (see Recommendation R4).

The demoscene — eliminate file loading entirely

werkkzeug and apEx answer the file-loading problem by mostly not loading files. A texture is not a PNG on disk — it is a PHXTEXTUREOPERATOR DAG that evaluates to a Texture2D at runtime. The graph stores ~48 bytes of parameters; the rendered texture is 1–16 MB. notes/per-demoscene/apex-public/texgen/, size-optimization.md

For a node-graph framework, the operator can be the asset

This is leverage a game engine does not have and Flux does. A GenerateNoise or GenerateGradient operator is a procedural asset — no path, no resolution, no decode, no bundle entry. The CachedResult "generate once, return cached pointer" pattern maps directly to a Rust OnceCell<wgpu::Texture>. The strategic consequence for Flux: the bundle only needs to contain genuinely external authored content (user photos, custom audio clips). Every asset that can be expressed as a deterministic subgraph should be — which shrinks the bundling problem from "pack everything" to "pack the irreducible minimum."

Game engines — the two mature editor↔shipped pipelines

Unity Addressables reconciles editor and shipped builds with a switchable mode: "Use Asset Database" loads loose editor assets directly; "Use Existing Build" exercises the exact runtime path against a pre-built catalog (a JSON manifest mapping address → bundle location). The catalog is the contract between build and runtime. Its AssetReference type stores only an identifier — no script field ever holds a raw, always-loaded texture. Unreal instead reconciles the two worlds by transformation: the cook runs all importers once and writes cooked binary, so the runtime only deserializes — it never re-decodes. Its hard/soft reference distinction (TObjectPtr always-loaded vs TSoftObjectPtr path-only) and IoStore's export-level byte-range I/O are both worth filing away as future directions. GK

5Synthesis — recurring patterns

Across fourteen frameworks, six patterns recur in the designs that hold up:

  1. The resolution / decode split is real where it matters. It appears independently in Bevy (AssetReader/AssetLoader), Cinder (DataSource→loadImage), three.js (FileLoader vs typed parse()), tixl (TryResolvePath/TryGenerate<T>) and Unity (IResourceLocation/IResourceProvider). It is fused in openFrameworks, cables.gl, TouchDesigner, vvvv and Babylon.js — and those are precisely the designs flagged as anti-patterns. Convergent independent evidence: the split is sound.
  2. Centralised resolution + a swappable backend solves the editor↔shipped split. Bevy's AssetSource (unprocessed/processed readers), Unity's catalog mode switch, tixl's IResourcePackage registry, and three.js's setURLModifier are the same idea: the same logical path resolves through an interchangeable backend, and operators above never learn which backend answered.
  3. A per-type decode registry keyed by extension or MIME type. Cinder's ImageIoRegistrar, Bevy's loader registry, three.js's addHandler, Babylon's plugin registry and Unity's providers all let a new format be added without touching call sites.
  4. Path-keyed deduplication. Where caching exists at all, the logical path is the cache key (Bevy, tixl, Unity, three.js, Unreal). Content-addressing by hash is rare — only Unreal's cooked GUIDs and Bevy's processed-asset hashing approach it.
  5. Pre-decoding for the shipped path. Unreal cooks; Bevy's processor writes optimised artifacts. The expensive decode happens once, at build time; the runtime only deserializes. The shipped runtime is faster and simpler than the editor.
  6. Sidecar metadata for import settings. Bevy's .meta files carry per-asset loader settings and survive into the processed pipeline — the contract between the editor and the packer.

6Anti-patterns & things that aged badly

Avoid — observed failure modes
  • A single global resolution root (openFrameworks' dataPathRoot). One mutable global string cannot serve an editor project root and a packed bundle simultaneously. Flux needs a context-parameterised resolver, never a global.
  • Fusing I/O + decode + GPU upload into one value object (oF's ofImage). It makes the node-graph model impossible — you cannot put half the pipeline in one operator and half in another.
  • Fused per-operator loaders (TouchDesigner, vvvv, cables.gl). No cross-operator dedup, no shared caching, and every new asset type needs a whole new operator family with the resolution logic copy-pasted in.
  • The "handle is a promise" model (Bevy's Handle<T>, Unity's AsyncOperationHandle). It leaks async into every consumer and assumes a persistent frame loop — directly incompatible with a synchronous graph evaluator.
  • Manual refcount release (Unity's mandatory Release()). An unreleased handle silently leaks the whole bundle. Rust's Drop makes this class of bug structurally impossible — do not reintroduce it.
  • Caching off by default (three.js's Cache.enabled = false). A footgun: most users never discover it. Cache on by default; invalidate on change.
  • Background-thread mutation of a shared object without synchronisation (Processing's requestImage() vessel, which relies on the Java memory model to eventually publish a pixel write). In Rust this is a data race the compiler rejects — it does not port.
  • A no-fallback error policy (Bevy, Unity, Unreal all leave substitution to the caller). A missing asset should degrade gracefully, not blank the output or abort evaluation.

7Recommendations for Flux

The proposed architecture, distilled from the evidence above. The shape is tixl's IResourcePackage + TryGenerate<T>, corrected for Rust and for the fact that a Flux bundle may never be extracted to disk.

R1 · Keep the resolution / decode split — it is validated

Adopt it as the substrate. Resolution is a format-neutral Resolver trait that maps a logical path to bytes. Decode is per-type, co-located with each asset domain. This is confirmed by five independent mature designs; no evidence argues against it.

R2 · Resolution = a Resolver trait with a swappable backend

Define the trait so it abstracts the I/O itself, not just path strings — this is the one place to go further than tixl, whose TryResolvePath returns an absolute filesystem path. A Flux bundle may be a memory-mapped blob that never hits disk:

trait Resolver: Send + Sync {
    fn resolve(&self, path: &AssetPath) -> Result<Bytes, AssetError>;
}
struct FilesystemResolver { roots: Vec<PathBuf> }   // editor
struct BundleResolver     { catalog: Catalog, blob: Mmap }  // packed runtime

Select the implementation once, at startup, by execution context. Adopt a Bevy-style path grammar — scheme://path#label — so embedded://shaders/blur.wgsl (built-in shaders baked into the binary) and sub-asset labels (a glTF mesh/material) need no new operator types.

R3 · Decode = a per-type registry, given a controlled re-entry into resolution

A HashMap<&str, Box<dyn Decoder>> keyed by extension/MIME (Cinder's ImageIoRegistrar pattern) lets third-party crates add formats. Critically, hand each decoder a &dyn Resolver — Bevy's LoadContext lesson — so a glTF or OBJ decoder can pull in its sibling buffers and textures. Express intra-format dependencies via this re-entry, not as graph nodes; reserve graph nodes for user-authored composition. (This boundary is genuinely unsettled — see Open Question 1.)

R4 · Synchronous loading: block-on-first-use, with an optional pre-warm pass

The decision that matters most

Every async-first design here (Bevy, Unity, Unreal, three.js) conflicts with Flux's synchronous evaluator. The closest analogue, tixl, is synchronous — its Lazy<T?> blocks on first GetValue and caches thereafter — and it works. Default to that. A LoadTexture operator resolves+decodes synchronously the first time it evaluates, caches the typed asset, and returns the cached value on every subsequent frame.

Layer one optimisation on top: a pre-warm pass — p5.js's preload() barrier, generalised. Before graph evaluation, walk the graph for Load* operators and resolve+decode them on a worker pool (Bevy's IoTaskPool is a fine mechanism to borrow). By evaluate() time the assets are cache hits and the hot path stays synchronous. Do not adopt the async-handle model where a downstream operator must handle a Loading | Ready(T) value — that reintroduces the frame-loop assumption Flux exists to avoid. The packed runtime has local assets anyway, so blocking is cheap there.

R5 · Lifetime: a central asset cache; operators hold IDs

The project memory already records that Flux rejected operator-owns-resources for GPU resources and wants centralised resource management. The asset layer should follow suit: a central cache/pool owns decoded assets and keys them by logical path for dedup; operators hold a lightweight AssetId, not an Arc<Asset>. Do not copy Bevy's distributed "last strong handle drop frees it" model — it scatters lifetime across the graph. tixl's FileResource Claim/Release refcounting at the cache layer is the right altitude for that logic.

R6 · Hot-reload: copy tixl's watcher → dirty-flag propagation

It is the only studied mechanism that propagates a file change correctly through a node graph, and it is synchronous-friendly. OS watcher on a background thread → debounced event queue → drained on the main thread at frame start → invalidate the cache entry by stable AssetId → mark dependent operator output slots dirty → the existing Flux dirty-propagation re-evaluates downstream. The async is confined to the OS watch thread. Editor only — the packed BundleResolver registers no watcher (tixl ships the Player with FileWatcher = null).

R7 · Bundling: a content catalog + a packed blob, with optional pre-decode

tixl copies raw files flat; the demoscene embeds a compact binary; Unreal cooks; Unity ships a catalog. Target the middle: a catalog (manifest mapping logical path → offset, length, content hash, format hint) plus a packed blob the BundleResolver memory-maps and resolves by offset. Consider moving Decode to pack time for the shipped runtime — transcode PNG → BCn, pre-compile shaders — so the runtime only deserializes (Unreal's cook, Bevy's processed assets). That makes "decode" have a bake variant. Carry per-asset import settings in a Bevy-style .meta sidecar.

R8 · Make procedural-generation operators first-class peers of Load*

The demoscene insight, applied: a node-graph framework should treat GenerateNoise, GenerateGradient and similar as first-class assets, not afterthoughts. Every asset expressible as a deterministic subgraph costs bytes of parameters instead of megabytes of data, and needs no bundle entry, no resolution and no decode. This shrinks the bundling problem to its irreducible core — the genuinely external, authored content.

R9 · Error handling: deterministic fallback assets, never an aborted evaluation

Improve on Bevy/Unity/Unreal here. The Decode layer should own deterministic fallback assets — a magenta checkerboard texture, a unit-cube mesh, an identity shader — so a synchronous graph evaluation always produces a frame even when a file is missing or corrupt. Surface the failure to the editor as an operator error badge (tixl's LogErrorState, TouchDesigner's red node), but never let a missing asset crash a packed runtime. Operator output type is Result<Asset, AssetError> with a typed enum — NotFound, DecodeFailed, BundleKeyMissing — so the evaluator can mark downstream operators errored without panicking.

8Open questions

Questions this research surfaced but could not settle:

  1. Where does decode-time sibling resolution live? Loader-driven recursion (Bevy's LoadContext, tixl tracing HLSL #includes) keeps the graph clean but couples decode to resolution and hides dependencies from the graph. Graph-expressed dependencies (separate LoadTexture nodes) are explicit but explode the node count for a glTF referencing a dozen textures. R3 proposes a hybrid — loader recursion for intra-format deps, graph nodes for user composition — but the exact boundary is unproven.
  2. Does block-on-first-use cause unacceptable editor hitches? tixl's synchronous Lazy works, but tixl-scale assets may be smaller than Flux's targets. A first-frame block on a large mesh or 8K texture could stutter the editor. The pre-warm pass mitigates it — at the cost of complexity. No measurements exist yet.
  3. Path-keyed vs content-addressed bundle keys. Path keys are simple and universal here; content hashes (Unreal's cooked GUIDs) enable cross-path dedup and incremental patch bundles. Whether Flux's bundle needs patchability is a product decision not yet made.
  4. Is pre-decode (cooking) mandatory or optional for the packed runtime? Cooking gives fast loads and a small, simple runtime, but a slow pack step and a hard coupling between the packer and the runtime's format version. Bevy makes processing optional (AssetMetaMode); Unreal makes it mandatory. Undecided.
  5. Do small data assets (CSV/JSON) want the same substrate? Texture/mesh/shader assets are large, decode-expensive and cache-friendly. A small JSON file is cheap to parse and may want to behave as a live-editable value in the graph rather than a cached binary asset. Whether one substrate fits both, or data files deserve a lighter path, is unresolved.
  6. Streaming genuinely large media. None of the synchronous-friendly references (tixl, Processing) actually stream. If Flux needs video or large point clouds, the synchronous model breaks down and likely needs a TouchDesigner-style escape hatch — background decode that presents the latest-ready frame. That is a deliberate exception to R4, not covered by the current design.
  7. Where does GPU upload happen? Decoding a texture yields bytes; turning them into a wgpu::Texture needs a device and queue. openFrameworks fuses upload into decode (an anti-pattern). Whether upload belongs in the Decode layer or is a separate step — and how it interacts with Flux's existing command-flow design for GPU work — needs to be reconciled with that adjacent work.
